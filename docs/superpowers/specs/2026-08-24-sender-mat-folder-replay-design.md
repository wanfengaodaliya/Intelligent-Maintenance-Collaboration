# Sender MAT 文件夹顺序重放设计

## 目标

支持三个 Sender 各选择一个包含 80 个 `.mat` 文件的目录。每个 Sender 将目录内文件按自然文件名顺序重放为一个任务的 80 个数据包，每个 MAT 文件对应一个 50ms 数据包。同时保留现有“单个 MAT 文件切分为多个窗口”的兼容模式。

## 接口与兼容性

CLI 继续使用现有参数形式：

```text
--source sender_id=PATH
```

`PATH` 可以是现有的 MAT 文件，也可以是目录：

- 文件：维持当前行为，从一个 MAT 记录切分 `expected_packet_count` 个窗口；
- 目录：只读取目录直属的 `.mat` 文件，不递归子目录；按自然文件名顺序排列；文件数必须等于 `expected_packet_count`。

配置、Scheduler 请求、MQTT 主题、包结构、任务编号、发送间隔、重试和确认逻辑保持不变。

## 数据流

目录模式由轴承场景的 `BearingInputAdapter` 处理：

1. 识别 source 是目录；
2. 收集直属 `.mat` 文件并按完整文件名自然排序；不同工况组保持分组，组内数字按
   `1, 2, ..., 10, ..., 20` 排序，不按文件修改时间排序，也不把各组相同尾号交叉；
3. 校验文件数恰好等于配置的预期包数；
4. 逐文件加载并在调度前准备每个文件的第一个 50ms 窗口；
5. 将窗口的包序号和窗口索引规范化为目录中的 1–80 顺序；
6. 交给现有 Sender 控制器按原有节奏、调度和 MQTT 流程发送；
7. 每包来源映射记录该包实际对应的 MAT 文件，而不是目录路径。

单文件模式继续走原来的 `MatRecord.windows()` 路径。

## 错误处理

目录模式在调度和 MQTT 发送前完成基本校验，并给出明确错误：

- source 路径不存在；
- 目录内没有 MAT 文件；
- MAT 文件数量与 `expected_packet_count` 不一致；
- 任一 MAT 无法解析；
- 任一 MAT 无法提供首个完整 50ms 窗口。

不跳过损坏文件，不静默改变包数，不递归读取嵌套目录。

## 测试与验收

- 自然排序正确：`*_2.mat` 位于 `*_10.mat` 之前；
- 目录中 80 个 MAT 产生连续的包序号 1–80；
- 每个包的来源映射指向对应 MAT 文件；
- 文件数不是80时在发送前失败；
- 单 MAT 文件旧行为和输出字节保持不变；
- 三个 Sender 仍并发运行，每个 Sender 独立选择一个目录；
- Sender、架构和完整项目测试通过；
- 使用临时的三组 80 MAT 目录完成真实 CLI 冒烟测试。

## 非目标

- 不修改 MAT 信号解析公式、50ms 窗口内容或包协议；
- 不修改调度、MQTT、Edge、Cloud 或数据库业务逻辑；
- 不自动推断 Sender 与文件夹的对应关系；
- 不支持一个 Sender 同时选择多个目录；
- 不将80个 MAT 文件合并或复制为新的数据文件。
