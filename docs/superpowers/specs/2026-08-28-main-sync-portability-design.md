# 主分支增量可迁移化同步设计

## 目标

在保留 `challenge-cup-application` 已完成可迁移化成果的前提下，合并最新 `origin/main`，仅对主分支新增或修改内容中的场景耦合进行增量改造。不得重复实现已有插件、契约、兼容层或测试能力，不得改变模型算法、调度语义、旧 API、MQTT 协议和数据库业务含义。

## 工作区保护

1. 记录当前分支、HEAD、工作区删除项和未跟踪文件。
2. 建立合并前本地备份分支。
3. 使用带未跟踪文件的临时 stash 保存用户工作区内容，使合并在干净工作区进行。
4. 合并和验证结束后恢复 stash；发生冲突时只处理本次合并涉及的文件，不删除用户内容。
5. 不推送或提交到 GitHub 主分支。

## 同步方式

采用 merge，不使用 rebase 或选择性 cherry-pick：

1. 拉取最新 `origin/main`。
2. 从当前分支与 `origin/main` 的 merge-base 分析主分支增量。
3. 将 `origin/main` 合并到 `challenge-cup-application`。
4. 对冲突逐项判断主分支功能变化与可迁移化依赖方向，保留两侧有效成果。

merge 能保留当前可迁移化分支历史，也能完整引入主分支关联提交，避免 rebase 改写历史和 cherry-pick 漏掉依赖。

## 增量改造规则

主分支增量按以下边界处理：

- 通用通信、生命周期、调度机制、重试、降级、指标和日志继续位于平台核心或现有服务层。
- 新增轴承数据读取、模型、标签、预处理、风险映射、动作规则、全局分析和存储职责通过 `scenarios/bearing` Provider 接入。
- 旧 `bearing_id`、旧 API、MQTT 字段和数据库字段仅在外部协议、Repository 或 `compatibility/bearing_v12` 中保留。
- Edge、Cloud、Scheduler、Sender 通用入口不得直接导入轴承插件；生产装配继续集中在 `bootstrap/scenarios.py`。
- 优先复用现有 `ScenarioRegistry`、通用契约、Provider、兼容 mapper 和架构测试，不创建重复抽象。
- 不修改模型权重、特征公式、标签顺序、阈值、调度规则、冲突判断和仲裁业务规则。

## 验证标准

1. 主分支最新提交成为当前分支祖先。
2. 用户原有工作区内容恢复且未被提交。
3. 主分支新增功能保留并通过其相关测试。
4. 场景依赖和参考场景架构测试通过。
5. 完整 Python 测试套件通过；环境依赖失败必须与代码回归分开说明。
6. Docker Compose 配置和启动预检通过。
7. Scheduler、Cloud、Edge 核心健康检查通过。
8. 不向 `origin/main` 或其他远程分支推送。

## 停止条件

出现以下情况时停止并报告：

- 必须改变模型算法、外部接口语义或数据库业务结构才能合并；
- 主分支行为与现有基线无法同时保留；
- 用户工作区内容与合并修改发生无法安全判断的冲突；
- 需要删除既有兼容能力或大范围重做已完成改造。
